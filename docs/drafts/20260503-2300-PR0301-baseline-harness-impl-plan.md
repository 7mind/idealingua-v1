## §3 sbt task definitions

### `regenerateGoldens` — `TaskKey[Unit]`

Scope: project root (declared at top-level via sbtgen `imports`).

Behavior:
1. Loads the in-scope `.domain` corpus via `LocalModelLoaderContext` (see §4).
2. For each `(lang, loadedDomain)` pair where `lang ∈ {Scala, Typescript, CSharp}`:
   - Builds an `UntypedCompilerOptions` with deterministic manifests (PLAIN layouts; pinned `izumiVersion = "test-harness"`; see §4 manifest builder).
   - Invokes `new TypespaceCompilerBaseFacade(options).compile(toCompile)` → `Layouted` → `Seq[ExtendedModule]`.
   - Filters out `RuntimeModule` instances; keeps `DomainModule` only.
   - Writes each `Module(ModuleId(path, name), content)` to `idealingua-v1-test-defs/golden/<lang>/<path>/<name>` with UTF-8 encoding, deleting any pre-existing file at that path.
3. Idempotent: running twice in a row produces no diff in the golden tree.

Implementation: pure helper class `izumi.idealingua.harness.GoldenGenerator` with method `regenerate(corpusRoot: java.nio.file.Path, goldenRoot: java.nio.file.Path): Unit`. The taskKey assignment:

```scala
regenerateGoldens := {
  val corpusRoot = (LocalRootProject / baseDirectory).value.toPath
    .resolve("idealingua-v1/idealingua-v1-test-defs/src/main/resources/defs/main-tests/source")
  val goldenRoot = (LocalRootProject / baseDirectory).value.toPath
    .resolve("idealingua-v1/idealingua-v1-test-defs/golden")
  izumi.idealingua.harness.GoldenGenerator.regenerate(corpusRoot, goldenRoot)
}
```

### `verifyGoldens` — `TaskKey[Unit]`

Same compilation pipeline as `regenerateGoldens`; in-memory comparison against on-disk goldens; fails on any byte difference.

For each `(lang, domain)` produced by the compile pipeline:
1. Materialize the expected output path `idealingua-v1-test-defs/golden/<lang>/<modulePath>/<moduleName>`.
2. If the file does not exist → fail with "Missing golden: …".
3. If file exists → read bytes, compare against `module.content.getBytes(UTF_8)`. On mismatch → fail with "Golden mismatch: …" naming the (lang, domain, file) triple of the first divergent file (per PR-03 §3 Layer A line 238).
4. Also enumerate the existing golden tree under `idealingua-v1-test-defs/golden/<lang>/`; if any file is on disk that the compile pipeline did NOT produce → fail with "Stale golden: …".

Exit code semantics: sbt task throws `MessageOnlyException` on failure (sbt converts to non-zero exit), succeeds silently on full match.

### `runWireFixtures` — `TaskKey[Unit]` (placeholder)

Body: prints `"runWireFixtures: placeholder — implemented in PR-03.2"` and returns. No fixture corpus directory exists yet.

### `runCrossLangInterop` — `TaskKey[Unit]` (placeholder)

## §4 Compiler integration

### Entry point

`TypespaceCompilerBaseFacade.compile(toCompile: Seq[LoadedDomain.Success]): Layouted`
at `./idealingua-v1/idealingua-v1-transpilers/src/main/scala/izumi/idealingua/translator/TypespaceCompilerBaseFacade.scala:11`.

Returns `Layouted(emodules: Seq[ExtendedModule])` where each `ExtendedModule.DomainModule(domain: DomainId, module: Module)` and `Module(id: ModuleId(path: Seq[String], name: String), content: String, meta: Map[String, String])`. Definitions:

- `Module` — `./idealingua-v1/idealingua-v1-core/src/main/scala/izumi/idealingua/model/output/Module.scala:3`.
- `ModuleId` — `./idealingua-v1/idealingua-v1-core/src/main/scala/izumi/idealingua/model/output/ModuleId.scala:3`.
- `ExtendedModule` and `Layouted` — `./idealingua-v1/idealingua-v1-transpilers/src/main/scala/izumi/idealingua/translator/TranslationLayouter.scala:8-22`.

### Why in-memory and not `TypespaceCompilerFSFacade`

`TypespaceCompilerFSFacade` at `./idealingua-v1/idealingua-v1-transpilers/.jvm/src/main/scala/izumi/idealingua/translator/TypespaceCompilerFSFacade.scala:13` calls `IzFiles.recreateDir(target)` (line 19) which deletes the target dir first, then writes files including bundled runtime modules (lines 21-24, 31-39) and an optional zip (lines 42-52). The harness wants:
- No bundled runtime in goldens (runtime is per-language fixed code, not generated per-domain — would inflate golden size and create cross-domain duplication).
- No zip output.
- Per-language target subdir, not a single `target` dir.

The base facade returns the in-memory layout; the harness then writes only the `DomainModule` entries (not `RuntimeModule`). This requires building options with `withBundledRuntime = false` and `providedRuntime = None`.

### Deterministic manifest builder

Default manifests use macro-driven values that drift across invocations. `BuildManifest.Common.example` at `./idealingua-v1/idealingua-v1-core/src/main/scala/izumi/idealingua/model/publishing/BuildManifest.scala:59-71` interpolates `MacroParameters.artifactVersion()` (line 70). `ScalaLayouter.scala:14, 160, 168` and similar in the TS / C# layouters interpolate `MacroParameters.projectGroupId()`, `sbtVersion()`, scalajs plugin versions, etc.

To prevent goldens from drifting on macro changes, the harness builds manifests with **deterministic** values:

```scala
object HarnessOptions {
  private val pinnedCommon = BuildManifest.Common.example.copy(
    izumiVersion = "test-harness",
    version      = ProjectVersion(version = "0.0.0", release = true, snapshotQualifier = "test")
  )

  val scala: ScalaBuildManifest = ScalaBuildManifest(
    common = pinnedCommon,
    layout = ScalaProjectLayout.PLAIN,        // avoids SBT layouter macro reads
    sbt    = SbtOptions.example.copy(scalaVersions = List("2.13.18", "3.8.3")),
  )

  val typescript: TypeScriptBuildManifest = TypeScriptBuildManifest(
    common = pinnedCommon,
    layout = TypeScriptProjectLayout.PLAIN,   // avoids YARN package.json emission
    yarn   = YarnOptions.example,
  )

  val csharp: CSharpBuildManifest = CSharpBuildManifest(
    common      = pinnedCommon,
    nuget       = NugetOptions.example,
    layout      = CSharpProjectLayout.PLAIN,  // avoids NUGET .csproj emission
    enableNUnit = false,
  )
}
```

Manifest definitions:

## §7 verifyGoldens implementation

In-memory comparison (chosen over `git diff --no-index` to avoid shell-out and CI git-availability assumption):

```scala
def verify(corpusRoot: Path, goldenRoot: Path): Unit = {
  val produced: Map[Path, Array[Byte]] = compileAll(corpusRoot)
    // for each (lang, ExtendedModule.DomainModule(_, m)) → key = goldenRoot/lang/m.id.path/m.id.name
    // value = m.content.getBytes(StandardCharsets.UTF_8)
  val onDisk: Map[Path, Array[Byte]] =
    walk(goldenRoot).filter(Files.isRegularFile).map(p => p -> Files.readAllBytes(p)).toMap

  val missing    = produced.keySet -- onDisk.keySet
  val stale      = onDisk.keySet -- produced.keySet
  val mismatched = produced.keySet.intersect(onDisk.keySet)
    .filterNot(p => java.util.Arrays.equals(produced(p), onDisk(p)))

  if (missing.nonEmpty || stale.nonEmpty || mismatched.nonEmpty) {
    val msg = formatDiffReport(missing, stale, mismatched)
    throw new sbt.MessageOnlyException(msg)
  }
}
```

Byte-strict equality on UTF-8-encoded `Module.content`. Failure output names the (lang, domain, file) triple of the first divergent file (per PR-03 §3 line 238).

## §9 Cross-build strategy

The harness module declares `crossScalaVersions := Seq("3.8.3", "2.13.18")` in its sbt artifact (matching `idealingua-v1-compiler` at `./build.sbt:1419-1422`).

This is feasible because the entire transitive dependency chain (`idealingua-v1-test-defs`, `idealingua-v1-runtime-rpc-scala`, `idealingua-v1-transpilers`, `idealingua-v1-core`, `idealingua-v1-model`, `idealingua-v1-compiler`) already cross-builds the same Scala-version pair. No code in the harness is Scala-3-only or Scala-2-only; the helper objects use plain Scala stdlib (`java.nio.file.{Path, Files}`, `scala.collection`).

If the executor encounters an unexpected Scala-3-only or Scala-2-only API in a transitive dep that breaks the harness's cross-build, the fallback is to mark the harness `Targets.jvm3.copy(...)` to a single Scala version and document the deviation as a blocker for IMPL-N to address. Not expected based on dependency analysis.

Recommendation: broader scope (all 28 `.domain` files under `main-tests/source/`). Documented in §5. **Unblocks**: orchestrator/user confirms recommendation OR explicitly narrows to `idltest/` 22 files only.

### R2 — Loader behavior on `izumi/test/clashing.domain` + `izumi/test/clashing/another.domain`

Two `.domain` files with similar names in nested directories. Either (a) they declare different domain IDs (loader treats them as distinct, no problem), or (b) they declare the same ID and the resolver fails via `DuplicateDomainsRule`. The plan does not pre-read either file's `domain` declaration; the executor will discover this at T2. **Unblocks**: T2 report — if (b), the harness must exclude one of them or rely on the existing pre-baseline behavior (whatever loaderTest.scala sees today is the contract).

### R3 — Manifest determinism not yet proven

The plan pins `Common.example.copy(izumiVersion = "test-harness")` and uses `PLAIN` layouts to avoid macro-based interpolation. There may be additional `MacroParameters.*` reads in the layouters reachable via PLAIN that the plan didn't surface (the audit was non-exhaustive). **Unblocks**: T2 first run — if a golden contains a non-deterministic substring (e.g., a build-time timestamp, a hostname), the plan extends `HarnessOptions` to neutralize that source.

### R4 — `CommandlineIDLCompiler.scala:283` Go reference

PR-02-D03 noted the compiler module hard-codes `IDLLanguage.Go -> "0"` at `CommandlineIDLCompiler.scala:283`. PR-03.1's harness depends on `idealingua-v1-compiler` (per the §2 sbtgen `depends` block). If by the time PR-03.1 lands the user has already started PR-02 IMPL-8 (Go deletion) and `IDLLanguage.Go` is gone, this line fails to compile and the harness's transitive build breaks. **Unblocks**: PR-03.1 lands before PR-02 IMPL-8 is started (the locked sequence per the meta-plan); or PR-03.1 depends only on `idealingua-v1-transpilers` (not `-compiler`) and re-implements the corpus loader path resolution.

### R5 — `verifyGoldens` cannot detect a partial language regression

If `regenerateGoldens` fails halfway (e.g., Scala completes, TS fails with `NotImplementedError` from some `???`), the goldens for Scala are written but TS is not. The next `verifyGoldens` run will compare against the partial goldens and fail noisily on the missing TS files. The plan doesn't pre-empt this — the executor handles it at T4 by running `regenerateGoldens` to clean exit before committing. **Unblocks**: clean run criterion in T4.

### R6 / F5 — TBLOB-divergence finding (out of scope for PR-03.1, urgent for PR-03.3)

§5 audit found that **all three transpilers diverge from the locked Q3 decision**. Scala emits Circe array-of-integers; TS and C# emit `???` (compile-time NotImplementedError of the transpiler output). The user must reconfirm Q3 before any PR-03.3 fixture authoring that includes TBLOB. **Tracking**: opens new follow-up F5 in tasks.md. For PR-03.1 itself, the corpus has zero TBLOB usage — F2 is `[x]` vacuous, but F5 captures the surfaced finding.

### R7 — `build.sbt` regeneration step

The autogenerated header at `./build.sbt:1-3` reads "DO NOT EDIT THIS FILE / IT IS AUTOGENERATED BY `sbtgen.sc` SCRIPT / ALL CHANGES WILL BE LOST". The executor must:
1. Edit `sbtgen/Deps.scala` only.
2. Run `./sbtgen.sc` to regenerate `build.sbt` and `project/plugins.sbt`.
3. Commit both `Deps.scala` and the regenerated files in the same commit.
4. Verify `git status` shows the expected pair of files modified, not just `Deps.scala` (which would silently break the build for anyone who doesn't run `sbtgen.sc`).

**Risk**: if `./sbtgen.sc` requires `scala-cli` and a working `JAVA_HOME` on the executor's machine that aren't present, the executor must arrange the toolchain. The repo already pins `scala-cli` via `sbtgen.sc:3` and `sbtgen/project.scala:1-2`. There is also a `flake.nix` (root) that may provide the toolchain; the executor confirms via `nix develop`.

### R8 — Layer A diff policy not enforced by PR-03.1

The PR-03 §3 Layer A "diff policy" (lines 207-218) requires future PRs that produce a Layer A diff to classify the diff as wire-affecting vs not, and update the spec doc on wire-affecting changes. PR-03.1 does NOT implement enforcement — there's no PR-template hook, no CI guard. PR-03.1 only ships the *baseline* and the verification task. The diff-policy enforcement is implicit (any PR that changes the goldens fails CI; the reviewer manually reads the diff). Documented for visibility.
